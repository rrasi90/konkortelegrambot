# قرارداد امنیتی تحویل محتوا

## اصل مهم

متن سؤال، گزینه‌ها و دادهٔ موردنیاز برای نمایش را از کلید پاسخ، توضیح گزینه‌ها و محتوای محرمانهٔ ارزیابی جدا نگه دارید. اگر یک JSON در پایگاه داده هم گزینه‌ها و هم کلید پاسخ را دارد، هرگز آن را بی‌واسطه به مرورگر ارسال نکنید.

## قرارداد API برای سؤال

پاسخ اولیه به کلاینت فقط شامل شناسهٔ عمومی آیتم، نسخه، متن سؤال، گزینه‌های مجاز، نوع نمایش و زمان پیشنهادی است. موارد زیر نباید پیش از ثبت و اعتبارسنجی پاسخ به کلاینت ارسال شوند:
- گزینه یا پاسخ صحیح؛
- توضیح کلید پاسخ و تحلیل گزینه‌های انحرافی؛
- شناسه یا محتوای سؤال‌های holdout؛
- metadata یا نگاشت‌هایی که بانک ارزیابی محرمانه را افشا می‌کنند.

بعد از پاسخ، Worker باید هویت کاربر و مجوز آیتم را بررسی کند، رویداد را با کلید idempotency ثبت کند، پاسخ را در سمت سرور نمره بدهد و سپس پاسخ تشریحیِ منتشرشده را برگرداند. تکرار همان درخواست نباید امتیاز یا اثر تشخیصی را دو بار اعمال کند.

## قواعد نگهداری

- جدول‌های learning_items و item_skill_mappings از نقش‌های anon و authenticated قابل خواندن نیستند؛ مسیر trusted server از مجوز سمت سرور استفاده می‌کند.
- نقش service_role فقط سمت سرور نگهداری می‌شود و هرگز وارد متغیر VITE یا bundle فرانت‌اند نمی‌شود.
- بانک holdout از queryهای عادی تمرین جداست و فقط از مسیر ارزیابی کنترل‌شده قابل دسترسی است.
- رویداد خام پاسخ نباید کلید پاسخ یا متن کامل سؤال محرمانه را کپی کند؛ پاسخ خام، زمان، نسخهٔ آیتم و شناسه‌های لازم کافی‌اند.
- endpointهای debug، خطا و log نباید payload کامل بانک سؤال یا tokenها را ثبت کنند.

## آزمون‌های منفی پیش از انتشار

1. کاربر عادی نتواند query مستقیم برای دریافت answer key اجرا کند.
2. درخواست بدون احراز هویت معتبر Mini App دادهٔ شخصی یا سؤال غیرمجاز نگیرد.
3. شناسهٔ آیتم holdout از مسیر تمرین به پاسخ قابل‌استفاده تبدیل نشود.
4. پاسخ تکراری با همان idempotency key اثر یادگیری تکراری ایجاد نکند.
5. تغییر نسخهٔ سؤال یا کلید آن، رویدادهای تاریخی و گزارش‌ها را بی‌صدا بازنویسی نکند.

در این مرحله، این سند و مایگریشن سیاست دسترسی را تعریف می‌کنند؛ Worker هنوز احراز هویت، تحویل محتوای واقعی یا grading را اجرا نمی‌کند.
