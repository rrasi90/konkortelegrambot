## اجزا

| جزء | مسیر | مسئولیت |
|---|---|---|
| مینی‌اپ | `apps/miniapp/` | رابط کاربری فارسی راست‌به‌چپ؛ صف امروز، نقشهٔ مسیر، تنظیمات |
| API | `apps/worker/` | اعتبارسنجی، ارکستراسیون، پایدارسازی اتمی‌شونده |
| موتور | `packages/learning-engine/` | منطق تصمیم خالص و قطعی؛ بدون I/O و فریم‌ورک |

| اسکریپت‌ها | `scripts/` | اعتبارسنجی و درون‌ریزی محتوا، سرور توسعه |

## اصول معماری

1. **جداسازی تصمیم از I/O:** موتور تابع خالص است؛ همهٔ داده‌ها به‌صورت یک snapshot (EngineState) به آن داده می‌شود. این یعنی تست واحد بدون مک و دیتابیس.
2. **رویداد خام تغییرناپذیر:** `answer_events` فقط درج می‌شود؛ وضعیت کاربر از رویدادها قابل بازسازی است.
3. **کلید سرویس فقط سمت سرور:** مینی‌اپ هیچ دسترسی مستقیمی به Supabase ندارد؛ همه‌چیز از worker می‌گذرد.
4. **idempotency:** ثبت پاسخ با `attempt_id` یکتا (به ازای هر کاربر)؛ تلاش تکراری همان نتیجهٔ قبلی را برمی‌گرداند.
5. **RLS به‌عنوان دفاع در عمق:** جداول پشت RLS هستند؛ سرویس با کلید نقش سرویس عبور می‌کند.

## جریان ثبت پاسخ

1. مینی‌اپ پاسخ را با `attemptId` به `POST /api/answers` می‌فرستد.
2. worker توکن نشست را می‌سنجد و کاربر را می‌خواند.
3. اگر `attemptId` قبلاً ثبت شده، همان گزارش قبلی برمی‌گردد (replay).
4. وضعیت موتور بارگذاری می‌شود (گره‌ها، یال‌ها، سؤالات، تسلط‌ها، کارت‌ها).
5. `applyAnswer` اجرا می‌شود: لایه‌های ۱ تا ۴ + پیام منتور.
6. نتیجه پایدارسازی می‌شود: رویداد پاسخ، به‌روزرسانی تسلط‌ها، کارت‌های بازنشانی/ساخته‌شده.
7. گزارش موج به کلاینت برمی‌گردد (بدون افشای کلید سؤال در صف).

## استقرار

- **worker:** `wrangler deploy` (پوشهٔ `apps/worker`)؛ متغیرهای محیطی در `.env.example`.
- **دیتابیس:** اعمال `supabase/migrations` سپس بذرها.
- **مینی‌اپ:** فایل‌های ایستا؛ در استقرار Cloudflare از binding سایز `assets` سرو می‌شوند؛ برای دامنهٔ تلگرام به HTTPS عمومی نیاز است.

محدودیت شناخته‌شده: پایدارسازی «answer event + mastery + cards» سه فراخوانی جداست؛ تراکنش اتمی واقعی به RPC یا Postgres function نیاز دارد (در نقشهٔ راه).
